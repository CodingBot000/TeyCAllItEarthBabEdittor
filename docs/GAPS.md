<a id="sys-001"></a>
## SYS-001 — 강화 코호트의 전력이 저장 스키마 범위를 초과

**오류 확인 · P1.** [conversionRules.ts](../src/game/domain/conversionRules.ts)의 `finalizeDebriefAllocation`은 전력을 `100 × (1 + conditioning×0.08)`로 생성한다. [saveRepository.ts](../src/game/infrastructure/persistence/saveRepository.ts)의 `cohortSchema.strength`는 0~100만 허용한다. 쓰기에는 검증이 없어 잘못된 상태가 활성 저장에 들어간다.

재현: 충분한 자원을 가진 캠페인에서 neural-foundry 1 → cohort-conditioning 1 구매 → 회수 포로 5,000명을 코호트 1개로 변환 → 저장 후 읽기. 전력 **108**, `campaignV5Schema.safeParse=false`, `loadCampaign=null`, `.corruptSave` 보존을 확인했다. 2~3레벨은 116·124로 같은 계약을 위반한다. 정상 신규 캠페인에서 재료를 모으는 전 과정을 수동 플레이한 것은 아니다.

영향: 강화 후 생성만으로 다음 새로고침의 계속하기가 사라질 수 있다. 원문이 남으므로 완전 삭제와는 구분해야 하지만 사용자에게 복구 수단은 없다.

결정·완료 조건: 전력을 백분율로 유지할지 최대 전력을 별도 스탯으로 둘지 정한다. 생성·피해·회복·스키마를 함께 맞추고 기존 108/116/124 저장도 복구한다. 레벨별 구매→변환→save/load 왕복과 실제 재접속 테스트가 필요하다. 단순히 100으로 잘라 강화 효과를 없애는 수정은 피한다.

<a id="sys-002"></a>
## SYS-002 — 포로를 남김없이 배분할 수 없는 상태

**오류 확인 · P1.** [conversionRules.ts](../src/game/domain/conversionRules.ts)는 코호트 5,000명 단위, 바이오매스 100명 단위, 예비고 상한, 정확한 인원 합계를 동시에 요구한다. 예비고 소비·폐기 경로는 없다.

재현: `captiveReserve=50,000`, 회수 포로 101명. LEGION/BALANCED/SUSTAIN 모두 `cohortCount=0, biomassCaptives=101, reserveCaptives=0`을 만들며 `BIOMASS INPUT MUST USE 100 CAPTIVES`로 거부된다. 수동 조절도 해법이 없다. 5,000과 100의 배수로는 101을 만들 수 없기 때문이다. 일반적으로 남은 보관 공간이 `회수 인원 % 100`보다 작으면 같은 문제가 생길 수 있다.

영향: 배분을 확정할 수 없고 pending이 다음 임무를 막는다. 리로드해도 pending을 다시 읽으므로 해결되지 않는다.

결정·완료 조건: 잔여 인원을 부분 변환·폐기·초과 보관 중 어디로 보낼지 정한다. 수용 공간 0~99, 포로 0/1/99/100/101 및 큰 수에 대해 항상 유효한 기본안 또는 명시적 해결 행동을 제공한다. 이미 막힌 저장의 pending도 처리 가능해야 한다.

## SYS-003 — 도시 유기물 풀과 런타임 생성량 불일치

**오류 확인 · P1.** [generateAbsorbableClusters.ts](../src/game/battle/gameplay/generateAbsorbableClusters.ts)의 방공호 우선 슬롯과 [BattleFleeingCrowdVisuals.ts](../src/game/battle/runtime/BattleFleeingCrowdVisuals.ts)의 `registerFleeingCrowdTargets`가 [자원 풀](../src/game/battle/gameplay/sideViewResourcePools.ts)의 잔량 제한을 우회한다.

재현: seed 90210의 서울 유기물 풀을 0으로 두고 세션 생성. 방공호 잔량 5,622와 6,041이 생긴다. 실제 런타임과 같은 군중 등록을 호출하면 5,000×5가 추가되어 **총 36,663**의 유기물이 존재한다. 도메인 세션만 검사하면 이 중 군중 25,000은 놓친다.

영향: 도시 고갈·잔존 인구·획득 포로 간 계약이 깨지고 같은 도시 반복 수확이 가능하다. 군중은 직접 지정한 보상으로 생성되어 Desert의 템플릿 보상 배율 경로도 다르다.

결정·완료 조건: 방공호와 외부 인원을 하나의 도시 인구/풀 예산에서 할당하거나, 재생되는 자원이라는 별도 사양과 회복 규칙을 명시한다. 유한 자원이 사양이면 ‘pool 0 → 흡수 가능 0’, 모든 생성 경로의 합계가 풀 이하, 재방문·저장/로드·프로필별 보상 일관성을 검증한다. 시각 클래스가 게임 자원을 생성하는 경계도 분리할 필요가 있다.

## SYS-004 — 현재 도시의 재출격은 편성 화면을 건너뜀

**흐름 누락 확인 · P1.** [WorldMapScreen.tsx](../src/game/presentation/screens/WorldMapScreen.tsx)의 `canEngage`는 현재 도시에서 `onEngage`를 선택한다. [GameApp.tsx](../src/game/GameApp.tsx)의 `enterBattle`은 새 편성 검증을 거치지 않고 요청을 만든다.

브라우저 재현: 새 캠페인 → 서울 편성·이동 → 전투·정산·배분 → 서울 상세의 ‘영공 진입’. 편성 화면 없이 주기 02 `CITY DAY` 전투에 들어갔다. 끝난 임무는 `plannedMission`이 비워져 기본 RAID·선택 코호트 없음으로 시작한다.

영향: 같은 도시를 돌파한 다음 점령 임무로 바꾸거나 새 병력을 선택하는 핵심 루프가 끊긴다. 다른 도시 왕복은 비용과 불필요한 임무를 추가하는 우회일 뿐이다.

완료 조건: 미확정 출격은 현재 도시에서도 편성으로 진입하고, 이미 확정된 임무의 재개만 그대로 허용한다. RAID→BREACHED→동일 도시 OCCUPATION, 코호트 재선택, 새로고침 후 재개를 실제 화면으로 검증한다.

## SYS-005 — 확정 임무 취소와 재편성 정책 부재

**흐름 누락 확인 · P2.** [GameApp](../src/game/GameApp.tsx)의 편성 `onCancel`은 화면만 지도 상태로 바꾼다. [logisticsRules](../src/game/domain/logisticsRules.ts)는 다른 `plannedMission`이 있으면 새 편성을 거부한다. 확정된 비용의 환불·임무 해제·도착 후 편집 명령은 없다.

재현 경로: 임무 확정·도착 → 지도로 돌아가기 → 다른 도시 편성 확정. 이전 임무가 남아 거부된다. 기존 목적지에서 확정 임무를 끝내는 경로는 남아 있으므로 모든 경우의 영구 진행 차단이라고 분류하지 않는다.

결정·완료 조건: 이동 전/이동 중/도착 후 각각 취소 가능 여부와 코어·셀 환불 정책을 정한다. 버튼 문구가 ‘취소’인지 ‘확정 임무 유지한 채 지도 보기’인지 구분하고, pending·transit·loadout 조합과 리로드를 테스트한다. 이동 타이머는 화면과 별도로 동작하므로 메뉴로 나가거나 재접속했을 때 자동 전환 정책도 점검한다.

## SYS-006 — 셀 비용은 있지만 소비하는 능력이 없음

**미연결 확인 · P2.** [combatRules](../src/game/domain/combatRules.ts)의 `heavyAbilityCellCost`는 항상 0이다. 반면 [편성](../src/game/domain/logisticsRules.ts)은 셀당 코어 8을 받고 [결과 처리](../src/game/domain/campaignRules.ts)는 남은 셀을 회수율에 따라 환급한다. `capacitor-rack`도 최대 셀 수만 늘린다.

도메인 재현: 셀 3개 편성 비용 24 → 오버드라이브 성공 후 **3→3**, 에너지 **1,000→600**. 기본 대파 회수율에서는 코어 4만 돌아온다. 브라우저에서도 셀 구매 없이 오버드라이브가 발동하고 18초 쿨다운·에너지 감소를 확인했다. 편성 설명은 여전히 발동마다 셀 하나를 소모한다고 한다.

영향: 전투 효용 없이 실패 시 코어를 잃는 구매 항목과 효과 없는 업그레이드가 남는다. 코어 충전 자체는 도시 이동에 쓰이므로 ‘코어 전체가 미사용’은 아니다.

결정·완료 조건: 최근 셀 제한 제거 의도를 유지한다면 구매·환급·저장 호환·capacitor-rack을 제거하거나 다른 효과로 전환한다. 셀을 되살리는 설계라면 명시적으로 결정한 뒤 비용과 HUD를 연결한다. 임의로 옛 제한을 복원하지 않는다. 0셀/최대셀·성공/대파/포기·기존 저장 보상에 대한 일관성을 확인한다.

## SYS-009 — 위협 예측 업그레이드의 현행 효과 없음

**미연결 확인 · P2.** `threatForecastMultiplier`는 [campaignRules](../src/game/domain/campaignRules.ts)에서 생성되고 [combatRules](../src/game/domain/combatRules.ts)의 `getTargetRecommendation`, `getTacticalRiskForecast`에서 읽힌다. 그러나 두 함수의 현행 런타임/HUD 호출이 없다. 실제 경보 증가도 줄이지 않는다.

**표시 오류 / 미연결 확인 · P3.** [DebriefScreen](../src/game/presentation/screens/DebriefScreen.tsx)은 모든 FAILED를 대파 제목으로 표시한다. 브라우저에서 선체가 남은 상태로 포기를 확정했는데도 ‘모선 대파 / 선체 파손’이 표시됐다. 실제 포기는 수리비·긴급 복구가 없는 별도 종료 사유다.

## SYS-018 — 바깥 군중까지 이동할 수 있는지가 화면비에 의존

**현행 공식으로 확인 · P2.** [createBattleRuntime](../src/game/battle/runtime/createBattleRuntime.ts)의 모선 이동 한계는 `max(52, visibleWidth×1.38)`, `visibleWidth=2×92×tan(17.5°)×화면비`다. [군중](../src/game/battle/runtime/BattleFleeingCrowdVisuals.ts)은 가장 바깥 X=±168에서 ±11 이동한다. [가까운 대상 선택](../src/game/battle/gameplay/sideViewBattleRules.ts)은 반경 5.8 + 업그레이드 레벨 + 2 이내다.

| 화면 크기 | 모선 최대 X | 기본 흡수 버튼이 닿는 최대 X | 바깥 군중의 가장 가까운 X |
| --- | ---: | ---: | ---: |
| 1280×720 / 640×360 | 142.33 | 150.13 | 157 |
| 900×500 | 144.11 | 151.91 | 157 |
| 1920×900 | 170.80 | 178.60 | 157 |

16:9에서는 beam-radius 3레벨이어도 153.13으로 157에 못 미친다. 도메인의 더 넓은 빔 유지 거리가 있어도 버튼이 최초 대상을 선택하지 못한다. 화면 밖 목표 안내는 도달 가능한 목표라는 보장이 없다. 이 표는 좌표 계산이며 각 화면비에서 직접 끝까지 이동한 브라우저 재현은 이번에 실행하지 않았다.

완료 조건: 전투 월드 경계를 화면 크기와 분리하고 카메라의 가시 영역만 조정하거나, 생성 영역을 실제 도달 범위에 맞춘다. 양 끝 군중·자원·SAM의 좌표 계약과 640×360/900×500/1280×720/1920×900 접근성을 검증한다.

<a id="sys-019"></a>
## SYS-019 — 기존 검증 실패와 과거 의존성 기록

**실행 확인 · P2.** 이번 `npm run lint`는 6 errors / 2 warnings로 실패했다. 소스 오류는 [BattleScreen.tsx](../src/game/battle/BattleScreen.tsx)의 effect 내부 동기 `setUnitPositionDefaults` 1개이고, 나머지 5개는 기존 `.vercel/output` 생성 번들의 display-name 오류다. [eslint.config.mjs](../eslint.config.mjs)가 이 경로를 제외하지 않는다. 경고 2개는 메인/지도 화면의 `<img>`다. 문서 정리에서 이 코드를 바꾸지는 않았다.

과거 마이그레이션 문서에는 npm audit·Node/ESLint 지원 범위·Editor CLI CJS/ESM 문제도 있었다. CLI wrapper는 남아 있지만 당시 취약점 개수나 버전 상태를 현재 사실로 재사용하면 안 된다. 이번에는 새 의존성 보안 검사를 수행하지 않았다.

완료 조건: 소스 lint 오류와 생성물 범위 문제를 분리해서 처리하고 CI와 동일한 Node/lockfile로 재검증한다. 의존성 변경은 별도 감사에서 현재 advisory와 실행·빌드·Editor 호환성을 확인한 뒤 결정한다.

## 보존한 후속 기획과 권장 작업 순서

완료된 흡수 V2·전투기 실제 3D 궤도·잔상 수정·지상 그림자·SAM 사격 위치 AI·자동 방어 업그레이드를 다시 ‘미구현’으로 계획하지 않는다. 반대로 과거 계획의 완료 체크가 현재 저장·경제·UI 회귀까지 보증하지는 않는다.

| 순서 | 묶음 | 착수 전 결정 / 산출물 |
| --- | --- | --- |
| 1 | 저장·배분·유한 자원 | SYS-001~003의 회귀 테스트와 기존 저장 복구 정책 |
| 2 | 출격·점령 핵심 루프 | SYS-004/005/010, 동일 도시 RAID→점령의 실제 플레이 검증 |
| 3 | 경제와 병력 역할 | 셀 유지 여부, 예비 포로 사용, 자동/수동 강하, 위협 예측 역할 |
