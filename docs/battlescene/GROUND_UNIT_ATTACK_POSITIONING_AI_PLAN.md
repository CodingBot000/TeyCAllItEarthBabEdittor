# 공통 지상 유닛 사격 위치 AI 및 SAM 이동 전투 개발계획

- 작성일: 2026-08-26
- 상태: **G0~G6 구현 및 검증 완료**
- 최초 적용 대상: 측면 전투의 실제 `FACILITY / SAM` 전투 개체
- 목표: 공격 가능한 위치를 스스로 찾아 이동하는 공통 AI를 만들고, SAM에 모선 기준 속도 70%와 좌·우 상향 20~40도 발사 조건을 적용한다.
- 아래 본문은 설계 기준이며, 실제 구현·검증 결과는 문서 끝의 구현 기록에 구분해 기록한다.

## 1. 요구사항과 적용 범위

### 1.1 사용자 확정 요구사항

| 항목 | 구현할 동작 |
|---|---|
| 이동 | SAM이 지상 X축을 따라 움직인다. 속도는 모선 이동속도의 70%다. |
| 반응 | 모선의 위치가 바뀌면 사격 가능한 위치를 다시 계산하고 따라 반응한다. |
| 너무 멀 때 | 모선 쪽으로 접근해 발사 구역을 확보한다. |
| 너무 가까울 때 | 모선이 차량 바로 위에 있는 등 발사 각도가 맞지 않으면 거리를 벌린다. |
| 화면 끝 | 화면 밖 방향으로 계속 밀지 않고, 가능한 다른 방향으로 이동해 사격 위치를 찾는다. |
| 발사 각도 | 현재 바라보는 좌/우 수평 방향에서 위로 20~40도 사이로만 발사한다. |
| 발사 대상 | 모선 이미지나 큰 시각 효과가 아닌, 현재 실제 피격범위로 발사 허용 여부를 판정한다. |
| 재사용 | 이동 AI, 공격범위 판정, 경계 처리 등 공통 파일을 SAM 전용으로 만들지 않는다. 다른 유닛은 자신의 공격범위 정책을 연결한다. |

### 1.2 이 계획에서 채택하는 기본안

사용자가 별도로 수치를 지정하지 않은 부분은 다음 기본안으로 명시한다. 구현 전에 변경할 수 있는 정책이며, 확정 요구사항과 구분한다.

| 미지정 항목 | 기본안과 이유 |
|---|---|
| 속도 70%의 기준 | 현재 측면 전투의 **기준 최고속도**에 0.7을 곱한다. 모선의 순간 속도에 곱하면 모선이 멈췄을 때 SAM도 이동하지 못한다. |
| 별도 최대 사거리 | 1차에는 신규 거리 상한을 임의로 만들지 않는다. 고도와 20~40도 각도 구역이 유효 수평거리를 정한다. 공통 정책에는 선택적 최소/최대 거리를 지원한다. |
| 히트박스 포함 조건 | 실제 피격영역의 일부라도 허용 발사 구역과 교차하고, 그 교차점으로 유효한 발사 방향을 구할 수 있으면 사격 가능하다. 모선 전체가 들어올 필요는 없다. |
| 이동 중 사격 | 1차 SAM은 정지 후 방향을 맞추고 사격한다. 이동 중 사격 허용 여부는 유닛 프로필로 분리한다. |
| 선회 | 1차는 좌우 스프라이트 전환으로 처리한다. 별도 포탑/차체 회전 애니메이션은 추가하지 않는다. |
| 발사 후 유도 | 20~40도는 **발사 순간의 제약**이다. 발사 후에는 기존 유도탄 성격을 유지한다. 전 비행구간을 직선 또는 20~40도로 제한하는 변경은 포함하지 않는다. |
| 화면 밖 개체 | 화면 밖에 원래 배치된 SAM을 화면 안으로 순간이동시키지 않는다. 정상 속도로 진입할 수 있지만, 화면 밖에서는 신규 사격하지 않는 것을 기본으로 한다. |
| EMP | 이동·선회·발사를 정지한다. 미발사 연사분은 취소하고, 정상 재발사 대기시간은 비활성 동안 정지하는 기존 방식에 맞춘다. 이미 발사된 탄은 유지한다. |
| 차량 간 충돌 | 이번 단계는 사격 위치 AI다. 차량 간 물리 충돌·도로 탐색·경로 그래프는 도입하지 않는다. 동률 목적지 선택은 ID 기반으로 분산할 수 있다. |

흡수 대상 `VEHICLE` 이미지는 실제 SAM 발사 개체와 다른 자원 대상이다. 동일 이미지를 사용한다는 이유로 이동·발사 AI를 붙이지 않는다. 다른 DEFENDER 및 시설의 기존 동작도 이번 단계에서 자동 변경하지 않는다.

## 3. 공통 코드와 SAM 전용 코드의 분리

### 3.1 구조 원칙

공통 AI는 `SAM`이라는 이름, 모선 이미지 크기, Babylon 메시, DOM, 카메라 객체를 알지 못한다. 숫자로 된 위치·경계·표적 체적과 공격 정책을 받아 이동 의도를 계산한다.

공격 정책은 두 가지를 제공한다. 첫째는 현재 위치에서 사격 가능한지와 유효 조준점이고, 둘째는 사격 가능한 지상 위치 구간이다. 공통 이동기는 이 구간을 경계와 결합해 목적지를 고른다. 각도나 거리 기준이 달라져도 이동기를 수정하지 않아야 한다.

표적 선택과 체적 제공은 어댑터의 책임이다. SAM 어댑터는 현재 모선 체적을 제공하지만, 공통 이동기에 모선 ID나 실드 규칙을 하드코딩하지 않는다. 다른 유닛은 지상 표적, 다른 피격 도형, 다른 거리/각도 정책을 제공할 수 있다.

| 계층 | 책임 | SAM에 한정되는 내용 |
|---|---|---|
| 공통 도형 | 타원체, 발사 구역, 광선/선분 교차 계산 | 없음 |
| 공통 사격 위치 계산 | 접근·이격·반대편 재배치·대기·경계 처리 | 없음 |
| 공통 이동 상태 | 위치 목표, 속도, 바라보는 방향, 선택한 진입 측면 | 없음 |
| 공격 정책 | 유닛별 공격 모양으로 사격해와 위치 구간 제공 | SAM은 상향 각도 구역 정책 선택 |
| 유닛 프로필 | 속도, 공격 모양, 정지 사격 여부, 소켓, 무기 리듬 | SAM 프로필의 0.7, 20도, 40도, 2발/0.3초 등 |
| 전투 연결 | 기존 시설 ID·체력·EMP·발사 이벤트와 공통 AI를 연결 | `facility.kind === 'SAM'` 연결 지점 |
| 런타임 표현 | 좌표 변환, 스프라이트 반전, 소켓, 디버그 표시 | SAM 원본 이미지와 로컬 소켓 설정 |

## 4. 좌표와 피격체적을 먼저 통일

### 4.1 현재 좌표 차이

현재 모선의 도메인 고도는 33이고 일반 렌더링 루트 Y는 16.5다. SAM의 도메인 발사 Y는 3.5지만, 기본 시각 소켓 Y는 `-16.5 + 4.6 = -11.9`다. 이 값을 섞으면 계산한 20~40도와 실제 화면 발사각이 달라진다.

1차 공통 계약은 기존 모선 도메인 고도 33을 유지하고, 평상시 `worldY = combatY - 16.5`인 **등방 단위의 평행이동**을 사용한다. X/Y 비율을 다르게 줄이는 변환으로 발사각을 바꾸지 않는다. 이 기준에서 기본 SAM 소켓의 combatY는 4.6이므로 기존 하드코딩 3.5를 그대로 사용할 수 없다.

`sideViewSpatialRules.ts`가 모선 판정 중심, 유닛 지상 pose, 방향별 소켓 pose와 world/combat 변환을 제공한다. 실제 루트 부모 변환·Z깊이는 구현 첫 단계에서 대조하여 같은 식으로 표현하고, 메시에서 읽은 결과와 오차 허용치 내 일치하는 회귀 테스트를 둔다. 시각 소켓을 읽어 AI를 돌리는 역의존성은 만들지 않는다.

모선의 흔들림·뱅크·회피 연출이나 이미지 바운딩 박스는 표적 체적을 변경하지 않는다. 파괴 cinematic은 신규 이동 AI와 사격을 정지한다.

### 4.2 실제 피격체적

현재 `BALANCE`에서 도출되는 반축은 다음과 같다.

| 실제 대상 | X/Z 반경 | Y 반높이 |
|---|---:|---:|
| 선체 | 9.45 | 2.10 |
| 실드 | 10.65 | 2.85 |

현재 SAM 충돌은 여기에 탄 반경 0.25를 더한다. 따라서 현재 동작 기준 유효 접촉체적은 선체 `(9.70, 2.35, 9.70)`, 실드 `(10.90, 3.10, 10.90)`이다. 새로 넓히는 탐지 반경이 아니라 기존 충돌 규칙의 수치다.

- `combatGeometry.ts`에서 기본 체적과 발사체별 유효 접촉체적을 한 번 정의한다.
- 발사 허용과 실제 탄 충돌은 동일한 **현재 SAM 유효 접촉체적**을 사용한다.
- 실드가 양수이면 실드, 0이면 선체를 사용한다. 실드 재생·소진 후 매 발사 시점에 재계산한다.
- `shieldVisualRadius`, `shieldVisualHalfHeight`, 모델 전체 크기, 전투기 keep-out 공간을 사용하지 않는다.
- 디버그 overlay의 배율은 표시 전용이다. AI 검사와 실제 도형을 함께 보여주는 새 표시에는 배율 1 기준선을 반드시 유지한다.
- 사용자가 디버그에서 확대·축소한 값을 실제 피격범위로 적용하는 기능은 별도 요구이며 이번 작업에서 조용히 추가하지 않는다.

### 4.3 방향과 발사 소켓

우측 원본의 소켓을 `localMuzzle`이라고 하면 방향 `facingX = +1 / -1`에 따라 소켓의 로컬 X도 같은 부호로 반전한다. 본체 이미지만 뒤집고 소켓은 원위치에 남겨두지 않는다.

체력바·문자 라벨은 뒤집지 않는다. 전투 판정용 소켓과 렌더링 소켓은 동일 pose 함수의 결과를 사용한다. UI의 지상 높이 디버그를 유지한다면 소켓의 공통 공간 컨텍스트까지 갱신해야 하며, 표현만 이동시킨 상태로 사격각을 계산하지 않는다.

## 5. 공격 구역과 사격 가능 위치

### 5.1 각도 정의

오른쪽을 바라볼 때는 +X 수평축, 왼쪽을 바라볼 때는 -X 수평축에서 위로 잰 각도다. 전역 극각으로는 오른쪽 20~40도, 왼쪽 140~160도에 해당한다.

발사 소켓 `S`, 같은 전투 평면의 목표점 `P`에 대해:

```text
h = facingX × (P.x - S.x)
v = P.y - S.y

필수 조건: h > 0, v > 0
theta = atan2(v, h)
발사각 조건: 20° ≤ theta ≤ 40°
```

양쪽 구역을 동시에 자신의 전방으로 간주하지 않는다. 왼쪽 목표를 쏘려면 먼저 왼쪽을 바라보고 그 방향으로 다시 검사한다. 뒤쪽·수직 아래·정확한 머리 위 점을 `abs(dx)`만으로 유효 처리하지 않는다.

### 5.2 중심점이 아닌 실제 도형과의 교차

판정 결과는 boolean만 반환하지 않고, 허용 구역 안에 있는 `aimPoint`, `launchDirection`, `launchAngle`, 현재 유효 피격체적 종류를 함께 반환한다. 모선 중심이 41도에 있더라도 실제 작은 피격영역의 일부가 39도에 있고 그 지점으로 광선이 닿으면 발사할 수 있다. 이때 미사일을 41도 중심 방향으로 생성해서는 안 된다.

1차 SAM은 고정 Z의 측면 발사 평면에서 계산한다. 3D 타원체를 단순히 화면에 투영한 외곽을 쓰지 않고 **소켓 Z에서의 실제 XY 단면**을 사용한다.

```text
k² = 1 - ((S.z - C.z) / rz)²
k² < 0 이면 이 발사 평면에서 피격체적과 교차 불가
단면 반경: a = rx × sqrt(k²), b = ry × sqrt(k²)
```

이 단면 타원과 20~40도 구역의 교차를 구하고, 반환한 조준점은 3D 유효 체적과도 대조한다. Z축 이동이 있는 다른 유닛은 다른 공격 정책을 연결할 수 있다.

- 타원의 접선 각도와 광선/타원 이차방정식을 이용해 정확한 교차 구간을 구한다.
- 중심·네 모서리 몇 점만 샘플링하거나 1도 간격으로 훑어 좁은 교차를 놓치는 방식은 사용하지 않는다.
- 접촉 경계는 포함하되 부동소수점 오차용 작은 epsilon만 허용한다. 20~40도를 실제로 넓히는 각도 여유값은 사격 허용에 쓰지 않는다.
- 공통 정책에 유한 사거리가 설정되면 같은 광선의 유효 거리 구간도 함께 검사한다.

### 5.3 지상 위치 구간 계산

점 표적이며 발사 소켓과 표적 사이 높이가 `H`일 때는 다음이 직관적인 출발식이다.

```text
최소 수평거리 = H / tan(40°)
최대 수평거리 = H / tan(20°)
```

현재 기본 시각 높이차 28.4를 사용하면 중심점 기준 약 33.85~78.03이다. **이는 설명용 값이며 실제 발사 판정은 타원체 교차로 계산한다.** 피격영역 가장자리가 닿는 경우 이보다 넓은 위치 구간이 가능하다.

표적 단면 전체가 소켓보다 위에 있는 일반 상황에서는 타원의 지지함수로 좌우 사격 가능 소켓 X구간을 직접 구할 수 있다. `C=(cx,cy)`, `H=cy-S.y`, 단면 반경 `a,b`일 때:

```text
R(theta) = sqrt(a² + (b × cot(theta))²)

오른쪽을 바라보는 소켓 위치 구간:
[cx - H×cot(20°) - R(20°), cx - H×cot(40°) + R(40°)]

왼쪽을 바라보는 소켓 위치 구간:
[cx + H×cot(40°) - R(40°), cx + H×cot(20°) + R(20°)]
```

소켓 구간을 차량 중심 X구간으로 바꿀 때 방향별 소켓 X오프셋을 빼야 한다. 높이가 교차하는 특수 상황, 거리 상한, 다른 모양은 해당 공격 정책의 별도 정확한 계산으로 처리한다. 이 공식의 가정이 맞지 않을 때 그대로 적용하지 않는다.

## 6. 이동 AI 동작

### 6.1 속도

현재 기준 `17 × 0.7 = 11.9` 월드 단위/초다. 11.9를 복사한 상수 대신 공통 기준 속도와 프로필의 `speedRatio = 0.7`로 계산한다.

모선이 정지하거나 감속 중이어도 SAM의 이동 능력은 유지된다. 1차는 일정 속도 이동과 목적지 도달 시 정지로 구현하며, 가속·제동이 필요해지면 공통 이동 프로필에 추가한다. frame delta를 곱하고 목적지를 지나치지 않게 이동량을 제한한다.

SAM이 모선보다 느리므로 모선이 최고속도로 계속 멀어지면 사거리를 잃는 것은 정상이다. 이를 보상하려고 SAM을 가속하거나 카메라 속도를 더하거나 순간이동시키지 않는다.

### 6.2 상태

| 상태 | 의미 | 이동/사격 |
|---|---|---|
| `APPROACH` | 현재 측면에서 너무 멀어 유효 구간으로 접근 | 접근, 사격 금지 |
| `RETREAT` | 너무 가까워 발사각이 높음 | 거리를 벌림, 사격 금지 |
| `REPOSITION` | 현재 측면 목적지가 막혔으나 반대편에 가능한 위치가 있음 | 반대편 목적지로 이동, 통과 중 사격 금지 |
| `HOLD` | 유효 위치에 정지하고 목표 쪽으로 방향을 맞춤 | 매 발 재검사 후 사격 |
| `WAIT_FOR_SPACE` | 경계 안에 가능한 사격 위치가 없음 | 정지, 발사 금지, 모선/카메라 변화 시 재평가 |
| `ENTER_VIEW` | 배치/카메라 변화로 화면 밖에 있지만 진입 경로가 있음 | 정상 속도로 진입, 신규 사격 금지 |
| `DISABLED` | EMP 등 비활성 | 정지, 사격 금지 |
| `NO_TARGET` / `DESTROYED` | 유효 표적 없음 / 유닛 파괴 | AI 중지 또는 제거 |

### 6.3 목적지 선택 순서

1. 최신 표적 체적과 차량 pose를 읽고 현재 위치의 사격 가능 여부를 구한다.
2. 현재 유효하고 정지해 있다면 불필요하게 움직이지 않고 `HOLD`를 유지한다.
3. 좌·우 방향별 사격 가능 차량 X구간을 계산한다.
4. 월드 경계와 화면 경계를 적용해 도달 가능한 구간을 구한다.
5. 현재 측면에 구간이 있으면 가장 가까운 안정적인 지점을 선택한다. 각도 경계보다 내부를 선호한다.
6. 현재 측면은 막혔고 반대편이 가능하면 `REPOSITION` 목적지를 확정한다.
7. 둘 다 불가능하면 `WAIT_FOR_SPACE`로 정지한다. 금지된 각도로 발사하지 않는다.
8. 이동을 적분하고 실제 새 위치에서 방향·소켓·발사 조건을 다시 계산한다.

머리 위처럼 좌우 비용이 같은 경우에는 직전 선택 측면을 우선하고, 초기 동률은 안정적인 유닛 ID/시드로 결정한다. 매 tick 무작위 방향을 선택하지 않는다.

반대편으로 재배치할 때는 모선 바로 아래의 일시적으로 더 불리한 구역을 통과할 수 있어야 한다. 매 프레임 순간 각도 오차만 줄이는 탐욕 이동은 경계에서 갇힐 수 있으므로 사용하지 않는다. `committedSide`, `goalX`를 유지하되 목적지가 실제로 불가능해지거나 모선 위치가 크게 달라지면 재계획한다.

### 6.4 떨림과 방향

목적지 비용에 이동거리, 경계 근접, 불필요한 측면 변경을 반영한다. 위치/각도의 작은 변화에는 기존 목적지를 유지하는 히스테리시스를 둔다. 선호각의 초기안은 30도지만, 30도 위치가 경계 밖이면 20~40도 내부의 도달 가능한 위치를 사용한다.

히스테리시스는 **이동 결정에만** 적용한다. 발사 각도가 19.9도/40.1도인데 기존 `HOLD`였다는 이유로 발사를 허용하지 않는다.

이동 방향 `moveDirectionX`와 바라보는 방향 `facingX`를 분리한다. 단일 차량 이미지의 1차 표현은 이동 중 이동 방향을 바라보고, 정지 사격 직전에 목표 쪽으로 선회한 다음 재검사한다. 향후 포탑 독립 회전이나 후진 이동을 추가해도 이동기·사거리 계산기를 바꾸지 않게 한다.

## 7. 화면 끝과 월드 경계

### 7.1 경계 정의

`현재 화면`은 브라우저 전체가 아닌 **배틀 캔버스의 실제 카메라 가시 영역**이다. 고정된 `initialViewHalfWidth`나 legacy `TACTICAL_MAP_BOUNDS`의 ±74로 대체하지 않는다.

런타임은 차량 렌더 깊이에서 카메라 frustum의 좌우 월드 X를 구한다. 차량 반폭과 안전 여백을 제외한 중심 이동 구간을 만들고, 프로필의 `worldMinX/worldMaxX`와 교차시킨다. 원근 카메라이므로 Z=0 기준 화면 폭을 모든 깊이에 그대로 쓰지 않는다.

```text
허용 중심 구간 = 월드 이동 구간 ∩ [화면 왼쪽 + 차량 반폭 + 여백,
                                    화면 오른쪽 - 차량 반폭 - 여백]
사격 목적지 구간 = 허용 중심 구간 ∩ 공격 정책의 사격 가능 위치 구간
```

SAM 월드 경계는 현재 프로필의 ±132를 출처로 삼는다. 화면 폭으로 계산되는 모선 이동 한계는 별도이므로 이 작업에서 모선 한계까지 조용히 바꾸지 않는다.

### 7.2 정지한 카메라의 경계 처리

유닛이 화면 끝에 도달하면 바깥쪽 이동량을 차단하고 속도를 0으로 만든다. 같은 바깥 방향을 계속 명령하지 않는다. 현재 측면에서는 사격 위치가 없으면 반대편 도달 가능 구간을 검사하고 그곳으로 재배치한다. 반대편도 없으면 대기한다.

경계에 닿았다는 이유만으로 무조건 속도 부호를 뒤집는 튕기기 이동은 사용하지 않는다. 뒤집은 방향이 어떤 사격 목적지로 이어지는지 확인해야 한다.

### 7.3 이동하는 카메라와 화면 밖 초기 배치

현재 맵에는 초기 화면 밖의 SAM도 있다. 모든 개체를 매 tick 화면 구간으로 강제 clamp하면 화면 끝으로 순간이동하고, 모선을 70% 속도로 추적한다는 조건도 깨진다.

따라서 다음 예외를 명시한다.

- 화면 안의 유닛이 자신의 이동으로 화면 밖으로 나가는 것은 차단한다.
- 카메라가 더 빠르게 움직여 차량을 추월하거나 화면 크기가 줄어 차량이 밖이 된 경우, 월드 위치를 보존한다. 필요하면 `ENTER_VIEW`로 정상 속도 복귀한다.
- 원래 화면 밖에 배치된 개체도 정상 속도로 진입한다. 보이지 않는 개체의 강제 재배치·복제는 하지 않는다.
- 화면 안에 계속 남도록 보장하면서 모선의 70% 최고속도까지 동시에 엄수하는 것은 카메라가 더 빠를 때 불가능하다. 본 계획에서는 속도와 월드 위치 보존을 우선한다.
- 가시 구간이 너무 좁아 전체 차량이 들어갈 수 없거나 합법적 사격 구간이 사라지면 `WAIT_FOR_SPACE`와 실패 이유를 기록한다.

리사이즈/카메라 이동 시 숫자 경계는 갱신하되, 고정 시뮬레이션 tick 안에서는 하나의 경계 스냅샷을 사용한다.

## 8. 발사, 연사, 미사일

### 8.1 매 발의 최종 발사 조건

`살아 있음 + 비활성 아님 + 유효 표적 있음 + 화면 사격 정책 충족 + 정지 사격 조건 충족 + 쿨다운 완료 + 현재 방향의 실제 체적 교차`를 모두 만족해야 한다.

현재 `tickSamSites`의 무조건 발사를 측면 모드에서 이 조건으로 대체한다. 별도 이동 AI와 기존 SAM 루프가 각각 탄을 생성하는 중복 경로를 만들지 않는다.

### 8.2 2발 연사 유지와 중간 조건 상실

- 첫 탄은 유효 사격해가 있을 때만 생성하고 기존처럼 0.3초 뒤 두 번째 탄을 예약한다.
- 두 번째 탄도 그 시점의 모선 피격체적, 차량 위치, 방향으로 검사한다.
- 첫 탄 이후 각도·화면·EMP·표적 조건을 잃으면 미발사 연사분은 취소한다. 오래된 두 번째 탄을 나중에 즉시 쏘기 위해 무기한 보관하지 않는다.
- 중단된 연사에는 일반 쿨다운을 적용한다. 조건을 잃고 되찾는 동작으로 연사 제한을 우회하지 못하게 한다.
- 아직 첫 탄도 쏘지 않았다면 각도 불충족만으로 쿨다운을 반복 재설정하지 않는다. 이동 중 일반 쿨다운은 감소하고 0에서 대기할 수 있다.
- 기존 일반 쿨다운 공식과 경계도/방어 배율은 유지한다. 첫 도입에서 공격 빈도까지 동시에 재조정하지 않는다.

### 8.3 발사 순간 스냅샷

새 탄에는 최소한 `sourceId`, 발사 시각, 방향별 소켓의 `launchPosition/launchY`, 유효 `launchDirection`, `launchAngle`, 최초 조준점 또는 표적 로컬 조준 오프셋을 보존한다.

차량이 이후 이동·선회·파괴되어도 이미 발사한 탄의 출발점은 변하지 않는다. VFX가 뒤늦게 생성되더라도 현재 차량 소켓을 다시 읽어 과거 탄의 출발점을 덮어쓰지 않는다.

### 8.4 유도와 실제 충돌

최초 이동 방향은 사격해에서 선택한 20~40도 방향이다. 기존 `tickMissiles`처럼 생성 직후 무조건 모선 중심으로 덮어써서 허용 각도를 벗어나게 하지 않는다. 선택한 표적 로컬 조준점으로 초기 유도를 시작하고, 이후 이동하는 표적을 추적한다. 실드 소진 등으로 조준점이 현재 체적 밖이 되면 현재 체적 내부로 재선정한다.

발사 당시 적법했다는 것과 명중은 별개다. 모선이 사격 구역을 벗어나도 비행 중인 탄은 기존 유도/수명 규칙을 따르고, 실제 접촉할 때만 피해를 적용한다. 요격·무적·실드/선체 피해 규칙은 유지한다.

새 좌표 계약의 탄은 `missile.position`을 공통 변환으로 그린다. 발사점과 현재 모선 사이의 거리비 보간으로 궤도를 다시 만들지 않는다. 미이전 전투기 탄은 명시적 legacy 어댑터를 유지할 수 있으나, 새 일반 좌표 경로를 `sam` 문자열에만 종속시키지 않는다.

공통 도형 모듈은 광선/선분과 타원체의 교차도 제공한다. 이동한 SAM 탄은 직전~현재 위치 선분으로 접촉을 검사해 큰 timestep에서 작은 피격체적을 건너뛰는 경우를 막는다. 기존 전투기 탄의 동작 변경은 별도 회귀 범위로 관리한다.

## 9. 데이터와 실행 순서

### 9.1 공통 계약 초안

아래는 구현할 책임을 나타내는 개략 인터페이스다.

```ts
type FacingX = -1 | 1;
type XInterval = { minX: number; maxX: number };
type FacingInterval = XInterval & { facingX: FacingX };

type ShotSolution =
  | { allowed: false; reason: string }
  | { allowed: true; aimPoint: Vec3; launchDirection: Vec3;
      launchAngleRadians: number; targetVolumeRevision: number };

interface GroundPositioningState {
  mode: PositioningMode;
  velocityX: number;
  facingX: FacingX;
  committedSide: FacingX | null;
  goalX: number | null;
  lastDecisionAt: number;
  blockedReason: string | null;
}

interface AttackPolicy {
  evaluateShot(query: AttackQuery): ShotSolution;
  findFiringIntervals(query: PositionQuery): FacingInterval[];
}

interface UnitCombatProfile {
  movement: { speedRatio: number; canFireWhileMoving: boolean };
  attackPolicyId: string;
  attackShape: AttackShape;
  muzzle: LocalMuzzlePose;
  boundary: BoundaryPolicy;
  weapon: WeaponSchedule;
}
```

`AttackShape`의 최초 구현은 `ELEVATION_SECTOR`다. 다른 공격 정책을 주입할 수 있는 계약만 확보하고, 아직 사용하지 않는 모든 도형을 선제 구현하지 않는다. 다른 각도/거리 정책을 쓰는 테스트용 유닛으로 공통 이동기 재사용성을 증명한다.

AI 상태는 `CombatState`의 공통 개체 키별 record 등 세션 데이터로 둔다. 콜백·Babylon 객체·DOM 참조는 저장하지 않는다. 위치의 원본은 계속 `CombatFacilityState.position` 하나이며, 별도 AI 위치와 렌더 위치를 서로 독립적으로 적분하지 않는다.

### 9.2 고정 tick 순서

1. 입력과 모선 이동을 계산한다. 실제 제한 후 속도와 위치를 현재 tick 값으로 기록한다.
2. 카메라 추적 위치를 갱신하고 현재 가시 경계의 숫자 스냅샷을 만든다.
3. 전투 시간·EMP·실드 등 해당 tick의 상태를 갱신한다.
4. 공통 공간 컨텍스트와 현재 피격체적을 만들고, SAM 어댑터를 통해 위치 AI를 실행한다.
5. 차량 위치를 반영하고 정지/방향/소켓을 확정한 뒤 매 발 사격 여부를 검사한다.
6. 적 미사일 이동·충돌·요격 및 기존 전투 규칙을 진행한다.
7. 지상 자폭드론·코호트·임무 판정 등은 최신 차량 위치를 읽는다. 파괴 처리 후에는 추가 발사하지 않는다.
8. 최종 상태에서 차량·소켓·탄·HUD·디버그 표시를 동기화한다.

현재 도메인의 `tickSamSites`는 `tickSideViewBattle`보다 먼저 실행된다. 따라서 후자 끝에 이동 함수를 추가하는 것만으로는 이전 위치에서 발사하는 문제가 남는다. **기존 발사 지점 직전에 공통 AI를 배치**하고 tick 내 순서를 위 기준으로 정리한다.

도메인은 런타임을 import하지 않는다. `CombatTickOptions` 등에 숫자로 구성된 측면 공간 컨텍스트를 전달한다. 측면 모드에서 컨텍스트가 누락되면 기존 무제한 발사로 우회하지 않고 이동/사격을 보류하고 진단을 남긴다. 테스트에는 명시적인 고정 컨텍스트 fixture를 제공한다. legacy 모드의 기존 동작은 별도 경로로 보존한다.

프레임률에 따른 의사결정 차이를 줄이기 위해 새 AI는 고정 스텝으로 실행하고, `advanceTime`과 일반 루프가 같은 적분 경로를 사용한다. 일시정지·전투 종료·파괴 cinematic에는 AI가 진행되지 않게 한다.

### 9.3 다수 유닛과 결정성

같은 tick의 표적 체적과 가시 경계는 한 번 계산해 공유한다. 현재 위치의 사격 조건은 매 tick/매 발 검증하고, 목적지 재선택은 기존 구간 이탈·경계 변경·표적 체적 변경 시 우선 실행한다. 1차 정책은 유닛당 고정 개수의 좌우 구간을 계산하여 월드 전체를 촘촘히 샘플링하지 않는다.

동일 입력·시드·경계 스냅샷에서는 같은 이동 결과가 나와야 한다. 시간에는 `state.elapsedSeconds`를 쓰고 `Date.now()`나 비시드 난수를 사용하지 않는다. 다른 해상도의 결과가 의도적으로 달라질 수 있는 부분은 가시 경계뿐이며, 테스트는 해당 경계 입력까지 고정한다.

## 12. 테스트와 수락 기준

### 12.1 순수 규칙 테스트

새 책임에 맞춰 `attackGeometry.test.ts`, `groundAttackPositioning.test.ts`를 추가한다. 기존 통합 행위는 `sideViewBattleRules.test.ts`를 확장한다.

| 시나리오 | 기대 결과 |
|---|---|
| 좌우 20도/40도 경계 접촉 | 해당 방향에서 접촉을 허용하고 도형 안의 조준점을 반환 |
| 19.9도/40.1도에 피격영역 전체가 있음 | 발사 불가. 이동 히스테리시스로 조건을 완화하지 않음 |
| 중심점은 구역 밖, 피격영역 일부는 안 | 교차 지점을 향하는 20~40도 발사해 반환 |
| 이미지/큰 실드 효과만 구역 안 | 발사 불가 |
| 모선 바로 위/뒤쪽/발사대 아래 | 현재 방향 사격 불가, NaN이나 잘못된 반전 없음 |
| Z투영만 겹치고 실제 단면은 없음 | 발사 불가 |
| 실드 소진·재생 | 활성 피격체적을 즉시 전환하고 오래된 사격해 폐기 |
| 모선 정지, SAM만 위치 확보 | SAM 이동 가능. 모선 순간속도 0에 묶이지 않음 |
| 속도 검증 | 정속 이동 시 `이동거리 / dt = 11.9`, 도착·경계에서는 그 이하 |
| 모선이 더 빠르게 도망감 | 사거리 이탈 가능. SAM 가속/순간이동/각도 우회 없음 |
| 너무 멀거나 가까운 초기 위치 | 각각 접근/이격 후 유효 위치에서 정지 |
| 현재 측면이 화면 끝에 막힘 | 반대편에 도달 가능한 구간이 있으면 재배치 후 사격 |
| 반대편 이동 중 머리 위 통과 | 목적지를 유지하며 통과, 좌우 무한 반복/중간 불법 발사 없음 |
| 양쪽 모두 가능한 위치 없음 | 정지 대기, 발사 불가 이유 표시. 표적 이동 후 재계획 |
| 초기 화면 밖/카메라 추월/리사이즈 | 월드 위치와 속도 한계를 지킴. 강제 화면 clamp 없음 |
| 여러 SAM의 동일 조건 | ID/시드 기준 결정적 선택, 우연한 매 tick 좌우 떨림 없음 |
| 2발 연사 사이 모선 이탈 | 두 번째 발사 금지, 연사 취소와 일반 쿨다운 적용 |
| 발사 이후 차량 이동·선회·파괴 | 이미 생성된 탄의 발사점 불변 |
| EMP 중/해제/파괴 | 이동·발사 중지, 해제 후 재평가, 파괴 후 재생성 금지 |
| 이동 목표에 드론·코호트 공격 | 현재 SAM 위치를 사용해 공격/충돌 |
| 30/60/120 FPS 및 큰 delta | 고정 스텝 결과가 허용 오차 내 일치, 체적 관통 누락 없음 |
| 다른 공격 정책 fixture | SAM 분기 추가 없이 다른 각도/거리 조건에 맞춰 같은 AI가 이동 |

정지 표적에 대해 도달 가능한 목적지가 있는 테스트는 최대 예상 이동시간과 소폭의 정지 여유 내 `HOLD`에 도달해야 한다. 해결 불가능한 배치에서는 성공을 강요하지 않고 `WAIT_FOR_SPACE`를 기대한다.

### 12.2 기존 테스트 변경 주의

현재 `sideViewBattleRules.test.ts`에는 “SAM이 모선 바로 아래에서 발사하며 `launchY=3.5`”를 기대하는 테스트와 “기존 거리/미사일 수 임계치를 넘어도 활성 SAM이 발사한다”는 테스트가 있다.

첫 테스트는 새로운 소켓 좌표와 유효 각도를 갖춘 fixture로 수정하고, 머리 위에서는 발사하지 않는 반례를 추가한다. 두 번째는 의도를 분리해 **금지 각도에서는 발사하지 않음**, **탄 수만으로 별도 제한을 새로 만들지 않음**을 각각 검증한다. 단순히 기존 실패 테스트를 삭제하거나 모든 기대값을 새 동작에 맞춰 느슨하게 바꾸지 않는다.

### 12.3 브라우저 검증과 관측값

`render_game_to_text`의 지상 개체 진단에 `x`, `velocityX`, `facingX`, `aiMode`, `goalX`, 선택 측면, `geometricallyEligible`, `canFire`, 실패 이유, 현재 가시 경계, 마지막 발사각·소켓 좌표를 추가한다. 기하학적으로 사격 가능하지만 쿨다운 중인 상태를 구분할 수 있어야 한다.

디버그 표시는 현재 활성 작은 히트박스, 현재 방향의 20/40도 선과 구역, 소켓, 선택 조준점, 목적지, 경계로 구성한다. 둘 다 사격 가능한 것처럼 보이지 않도록 반대 방향 후보 구역은 별도 후보 스타일로만 표시한다.

기존 `verify-side-view-visual-sync.mjs`를 확장해 상태·차량·소켓·탄을 비교하고, 복합 시나리오는 전용 `verify-ground-unit-positioning.mjs`에서 반복한다. 기존 runner와 서버/브라우저 설정을 재사용한다.

최소 캡처는 좌측/우측 사격, 머리 위 이격, 화면 끝 반대편 재배치, 막힌 배치 대기, 카메라 이동 후 재반응, EMP 정지다. 1280×720 및 기존 900×500·640×360 모바일 뷰포트에서 실제 캔버스 기준 경계를 확인한다. 각 시나리오를 새 세션에서 실행하고 스크린샷·상태·콘솔/네트워크 오류를 함께 검토한다.

구현 후 검증 명령은 `npm run typecheck`, `npm run test`, `npm run lint`, `npm run build`, 관련 브라우저 검증 및 기존 전체 전투 흐름이다. 기존 lint 실패와 새 변경으로 발생한 실패는 구분해서 보고한다.

## 14. 구현 기록 — 2026-08-26

- 공통 도메인 모듈과 SAM 프로필/어댑터를 위 경로에 구현했다. `CombatState.groundUnitAi`는 전투 세션에만 유지하며 저장 스키마는 변경하지 않았다.
- `GroundBattleRoot`의 Editor 변환은 항등이다. 실제 SAM 루트 Z=1.1, 소켓 로컬 Z=-1이므로 발사 평면 Z=0.1을 사용한다. 초기 Y=3.5는 실제 소켓의 combatY=4.6으로 의도적으로 보정했다.
- 상향 각도 정책은 타원 접점·광선 이차방정식으로 사격해를 구한다. 선택적 거리 제한은 원/타원 교차와 연속 다항식 근 계산으로 처리하며, 높이 교차와 유한 거리 위치 구간도 지원한다.
- 목적지는 가장 가까운 도달 가능 구간의 내부 2유닛(좁은 구간은 중점)을 선호한다. 기본 30도 중앙각은 발사해 선택에 적용하고, 차량을 불필요하게 더 움직이지 않도록 위치 선정은 가까운 내부점을 우선한다.
- 카메라 추적 직후 차량 스프라이트 깊이 Z=0.1의 가시 폭을 계산한다. 화면 안에서는 반폭 4와 여백 0.5를 제외하고, 화면 밖에서는 위치를 보존하며 11.9/초 이하로 복귀한다.
- RAF와 `advanceTime`은 공통 60Hz 누적기를 사용한다. 실시간 프레임 지연은 기존 제한 취지를 유지해 최대 0.25초까지만 따라잡고, 명시적 `advanceTime`은 전달된 시간 전체를 고정 스텝으로 처리한다.
- 새 미사일은 `coordinateSpace='SIDE_VIEW_COMBAT'` 계약으로 실제 위치를 렌더링한다. 전투기 탄은 명시적인 legacy 시각 어댑터를 유지했다.
- `COLLISION DEBUG`는 배율과 독립적인 실제 접촉체적 기준선, 현재 방향 구역, 소켓, 조준선, 목적지, 허용 경계를 표시한다. 반대 방향 구역은 현재 사격 방향으로 표시하지 않는다.
- 기준선은 Vitest 57개/typecheck 통과. 기존 전체 lint 실패는 `BattleScreen.tsx`의 `react-hooks/set-state-in-effect` 1건, img 경고 2건이다. 해당 UI는 이번 작업에서 수정하지 않는다.
- 최종 규칙 검증: 전체 95개 테스트, typecheck, production build, 변경 파일 ESLint, `git diff --check` 통과. 공간 테스트는 Editor 변환과 Babylon NullEngine의 실제 소켓 행렬까지 대조했다. Node NullEngine의 OffscreenCanvas 한계가 있는 GUI 파괴 효과 검증은 실제 브라우저 E2E로 수행했다.

### G6 브라우저 결과

- `SIDE_VIEW_BASE_URL=http://localhost:3000 npm run test:e2e:ground-positioning`: 성공. 1280×720, 900×500, 640×360에서 각 12개 발사 스냅샷, 좌·우 양방향 20~40도, 속도 상한, 실제 소켓과 탄 좌표를 검증했다.
- 정상 카메라 이동으로 `ENTER_VIEW → RETREAT / REPOSITION`을 재현했다. 리사이즈에서 순간이동이 없으며, EMP 중 두 SAM의 위치·방향·발사가 멈추고 해제 후 재개함을 확인했다. 일시정지와 파괴 cinematic에는 전투 시간이 진행되지 않았다.
- 기본 배틀 캔버스는 화면 크기와 관계없이 16:9를 유지한다. 따라서 공간 부족 검증은 테스트 페이지에만 CSS로 실제 캔버스 폭을 360px로 제한한 별도 fixture다. 숫자 AI 경계를 조작하지 않았으며, 실제 frustum이 좁아진 뒤 전 SAM이 `WAIT_FOR_SPACE`, 신규 SAM 탄 0개인 상태를 확인했다. 이 CSS는 제품 코드에 들어가지 않는다.
- 기존 시각 동기화, 900×500/640×360 모바일 조작, 임무 포기·저장 격리, 모선 추락/지면 충돌/실패 정산, 캠페인→전투→흡수→철수→정산→업그레이드 전체 흐름 검증도 통과했다. 전체 흐름에서 MACHINERY 자원 5,228 감소와 캠페인 저장 반영을 대조했다.
- 최종 production build를 3011 임시 서버에서 실행해 debug query 무시·실제 캠페인 저장 보존도 확인했다. 검증 후 임시 서버를 종료했으며 기존 3000 개발 서버는 유지했다.
- 오래된 전체 흐름/포기 검증의 버튼 선택자와 결과 제목을 현재 UI에 맞게 수정했다. 모선 이동 검증은 가속·감속까지 포함해 정지한 뒤 흡수하도록 보정했다. 게임 UI 자체는 변경하지 않았다.
- 표준 `develop-web-game` 클라이언트도 실행하고 캡처를 직접 검토했다. 최종 브라우저 시나리오의 콘솔·페이지·네트워크 오류는 0건이다.
