## 0. 이 문서의 목적과 실행 금지 범위

사용자는 오늘 실제 변경 없이 이 대화의 모선 계층화·실패·복구 과정을 기록하고, 다른 날 다시 계층화를 진행할 때 같은 실수를 방지하기를 요청했다.

**이 문서는 기록과 향후 작업 계획일 뿐, 계층화 재실행에 대한 승인이 아니다.** 문서 작성 작업에서는 새 Markdown 파일 하나만 만든다. 코드·장면·에셋·설정·`progress.md`는 수정하지 않으며, 에디터 조작, 장면 생성·패키징, 개발 서버 재시작, 빌드, 커밋·푸시·배포도 하지 않는다. 아래의 실행·검증 절차는 사용자가 나중에 실제 작업을 요청했을 때만 적용한다.

근거는 이 대화, 기존 `progress.md`, 관련 Git 커밋과 문서 작성 시점의 코드·장면 파일이다. 이번 문서 작성 중에는 에디터나 게임을 실행하지 않았다. 따라서 과거의 화면 검증 보고와 이번에 파일로 재확인한 사실을 구분한다.

## 1. 다음 작업자가 먼저 알아야 할 결론

모선 파츠를 `TransformNode` 아래에 넣는 행위 자체가 게임과 양립할 수 없는 것은 아니다. 사고 당시에는 다음 문제가 겹쳤다.

1. 에디터 저장 형식과 게임용 패키지의 부모 참조 형식이 달랐다.
2. 에디터 소스와 정상 동작하던 게임 패키지가 이미 일치하지 않았다.
3. 에디터 저장·패키징이 모선 외의 배경·프로토타입 관계와 모선 높이에도 영향을 주었다.
4. 복구 과정에서 관리용 그룹만 해제하지 않고 게임이 의존하는 Gameplay/Visual Root·소켓 관계까지 평탄화했다.
5. 부모 개수, 빌드 성공, 콘솔 오류 없음만으로 화면이 정상이라고 너무 일찍 판단했다.

현재 상태는 이전 커밋을 통째로 되돌린 상태가 아니다. **모선 파츠는 저장 파일에서 평탄하지만, 게임 로딩 시 코드가 기능상 필요한 부모를 다시 연결하는 복구 구조**다. 다음 계층화에서는 이 코드까지 포함해서 비교해야 한다.

### 명령의 실제 범위

- `npm run generate:battle`은 `node scripts/pack-editor.mjs --battle`을 실행한다. `create-battle-editor-scene.mjs`를 실행하는 명령은 아니다.
- 하지만 `--battle`은 “모선만 패키징”이라는 의미도 아니다. 현재 래퍼는 프로젝트 packer를 호출하고, 생성된 스크립트 맵을 정리하며, `assets/battlescene`을 `public/assets/runtime/battlescene`으로 다시 복사한다. 관련 public 산출물도 바뀐다.
- 현재 생성기는 `assets/battlescene.scene`을 제거한 뒤 전체 장면을 재작성하고, `project.bjseditor`도 기록한다. Graph 정리를 위해 이 생성기를 무심코 실행하면 사용자가 편집한 값까지 덮어쓸 수 있다.

이 문서 작성 중 위 명령들은 실행하지 않았다.

1. **배경 7개가 모두 같은 방식으로 끊긴 것은 아니다.** 기존 로그에는 “7개 Plane의 parentId 소실”이라고 쓰였으나, 정확히는 남아 있는 배경 Plane 6개가 부모를 잃었고 `CloudRoot`와 `CloudRootPlane`은 패키지에서 누락됐다.

## 6. 기술적 원인과 다음 시도의 위험 지점

### 6.1 에디터 부모 메타데이터와 런타임 부모 참조

당시 Editor 5.4.2 조사에서는 에디터 소스가 `metadata.parentId = parent.uniqueId`를 사용한다고 확인했다. 현재 설치된 CLI의 `node_modules/babylonjs-editor-cli/build/src/pack/scene.mjs`에서도 이 메타데이터를 `parentId`로 옮기는 처리를 확인할 수 있다.

`id`, `uniqueId`, `parentId`, `metadata.parentId`, 파일명은 같은 개념이 아니다. 이 프로젝트의 public 자료에는 문자열 `id`와 숫자 `uniqueId`·부모 참조가 함께 사용된다. 부모 ID를 해석할 때 문자열 이름만 대조하거나 파일명만 같다고 판단하지 않는다. 실제 설치 버전의 로더가 어떤 참조를 해석하는지 확인한다.

`parentId`가 59개 존재한다는 검사만으로 부족하다. 그 ID가 실제 부모로 해석되는지, 사이클·중복 ID·고아 그룹이 없는지, 최종적으로 같은 VisualRoot에 도달하는지를 확인해야 한다.

### 6.2 부모는 폴더 이상의 역할을 한다

부모 관계는 이동·회전·스케일·활성 상태·자식 검색에 영향을 준다. 현재 런타임은 하위 메시 검색으로 모선 발광, 탐색 빔 이미터, 렌더링 그룹 등을 설정한다. 소켓은 발사와 VFX 위치 기준이다. 모양이 잠깐 맞아도 이 연결이 끊기면 동작 중 문제가 발생한다.

특히 현재 저장 소스는 모선 파츠가 루트에 있고, 실행 시 부모를 다시 붙인다. **평탄한 소스 파일에서 계산한 월드 좌표를 그대로 “정상 게임의 월드 좌표”로 삼으면 안 된다.** 기준은 정상 런타임이 보정을 마친 뒤의 모선 형태·좌표·경계다. 에디터 로컬 좌표와 실행 중 월드 좌표를 각각 기록한다.

새 관리용 부모는 기본적으로 위치 0, 회전 0, 스케일 1인 상태를 사용하고, 기존 모선 루트의 위치·스케일을 중복 복사하지 않는다. 부모 교체 API가 월드 변환을 보존하는지, 로컬 값을 그대로 두는지 설치 버전에서 확인한다. 재부모화 전후 월드 행렬과 bounding box를 실제로 비교한다.

### 6.3 저장된 배율과 런타임 배율은 별도다

작성 시점 VisualRoot의 저장 스케일은 `[1.55, 1.15, 1.55]`이며 런타임은 여기에 `BALANCE.mothership.visualScale`을 `scaleInPlace`로 적용한다. 현재 배율은 1.5다. 변환 누적이 없다는 전제의 VisualRoot 유효 로컬 스케일은 `[2.325, 1.725, 2.325]`다.

실행 중 이미 확대된 값을 에디터 소스에 저장한 뒤 다시 1.5를 곱하면 크기가 바뀐다. 그룹화와 동시에 배율 적용 위치를 옮기거나 런타임 보정 코드를 제거하지 않는다. 장면 재로드·게임 재진입에서도 한 번만 적용되는지 확인한다.

### 6.4 배경 패널은 Root와 실제 Plane이 연결돼 있어야 동작한다

패널은 레이어 Root의 Y를 바꾼다. Plane이 자식이 아니면 숫자는 바뀌지만 실제 배경은 움직이지 않는다. 이번 사고에서 실제로 관찰된 증상이다.

모선 그룹 작업 전후에는 Sky/Cloud/Far/Middle/Near/Ground/Foreground 7개 레이어 각각의 Root, Plane, geometry, material, texture, 부모 관계를 비교한다. 구름 파일과 텍스처가 존재하는 것만으로 충분하지 않다. Plane과 실제 geometry가 패키지에도 포함돼야 한다.

### 6.5 정상 화면을 가리던 부수 문제는 계층 자체와 구분한다

부모를 잃은 프로토타입은 기존의 자식 검색 기반 숨김에서 누락돼 회색·보라 사각형과 구체로 노출됐다. 복구 때는 장면 전체의 이름 기준으로 숨기도록 변경했다.

충돌 영역 디버그 메시도 패널이 닫혀 있을 때 보이는 문제가 있었다. 이를 패널 열기·닫기에 연결했다. 이후 사용자가 별도로 요청해 되살린 “실제 쉴드 피격 시 모선 전체 bubble”은 이 충돌 디버그 메시와 다른 효과다. 다음 그룹화에서 청록색 메시가 보인다는 이유만으로 쉴드 VFX를 지우지 않는다.

## 7. 작성 시점에 남아 있는 복구 구조

현재 HEAD는 이미 복구 이후 다른 기능들이 추가된 상태다. 아래는 오늘 읽기 전용으로 확인한 데이터·코드이며, 내일의 상태가 같다고 가정하지 않는다.

| 항목 | 작성 시점 값 또는 동작 |
| --- | --- |
| 에디터 모선 파츠 | 59개, `metadata.parentId` 없음, 관리용 그룹 없음 |
| public 모선 파츠 | 59개, `parentId` 없음, 관리용 그룹 없음 |
| 모선 높이 | 소스/패키지 Y=16.5, 런타임 `MOTHERSHIP_Y=16.5` |
| 카메라 기본 기준 | Y=5, Z=-92, target Y=5 |
| 구름 | 소스·public에 Root와 Plane이 있으며 Y=4, Z=27, 크기 360×202.5 |
| 구름 소스 참조 | CloudRoot uniqueId=1001, CloudRootPlane uniqueId=1002, Plane의 editor parent=1001 |
| SAM / 공통 지상 기준 | SAM Y=-16.5 / 다른 공통 지상 기준 Y=-18.5 |
| 일반 배경 부모 복원 | 런타임에서 각 Plane을 레이어 Root에 연결 |
| 구름 누락 보정 | Plane이 없으면 런타임에서 생성하는 fallback도 남아 있음 |

`restoreMothershipRuntimeHierarchy(scene)`는 다음을 수행한다.

- GameplayRoot를 AirBattleRoot에 붙이고 Y=16.5를 적용한다.
- VisualRoot를 GameplayRoot에 붙인다.
- ModelRoot가 있으면 VisualRoot에 붙인다.
- 이름이 `mothership-`로 시작하고 부모가 없는 메시만 VisualRoot에 붙인다.
- Weapon/Drone/VFX 소켓 및 소켓 leaf 부모를 다시 연결한다.

**다음에 분류 그룹을 만들면 이 helper가 모든 오류를 자동으로 고쳐줄 것이라고 기대하지 않는다.** 그룹에 부모가 잘못 붙은 메시도 `mesh.parent` 자체는 존재하므로 위의 “부모 없음” 보정 대상이 아니다. ModelRoot 아래 분류 그룹까지 이어지는 완전한 체인을 따로 검증해야 한다.

또 현재 생성기는 여전히 6개 그룹을 생성하지만, 당시 제거한 `preserveEditorParentMetadata` helper는 없다. 생성기를 다시 실행하면 현재 평탄한 에디터 소스와 다른 데이터가 만들어질 수 있다. 현 복구 코드가 있는 상태에서 전체 생성기를 재실행하는 것은 별개의 위험 작업이다.

## 8. 당시 검증과 커뮤니케이션에서 잘못된 점

- Graph 재열기 성공을 전체 장면 성공으로 확장해 해석했다.
- 에디터 소스만 원복한 상태와 로컬호스트 반영 상태를 처음부터 분리해서 설명하지 못했다.
- 그룹 개수·부모 개수만 보고 평탄화 성공을 게임 복원 성공처럼 보고했다.
- TypeScript·Vitest·build 통과와 콘솔 오류 없음으로 시각 회귀까지 통과했다고 표현했다. 이 검사들은 잘못된 부모·Y값·누락 Plane을 충분히 검출하지 못했다.
- 캡처에 잘못된 위치와 프로토타입 노출이 보였는데도 정상이라고 결론 내렸다.
- 구름 크기·위치 설명에서 public 저장값과 런타임 덮어쓰기 값을 혼동했다.
- 복원 과정에서 단계별로 검증하지 않은 보정까지 한꺼번에 정상화라고 보고했다.

다음에는 “파일 구조 확인”, “에디터 재열기 확인”, “실제 플레이 회귀 확인”, “사용자 외형 확인”을 별도로 보고한다. 확인되지 않은 항목은 미검증으로 남긴다. 테스트가 시작 메뉴에서 끝났거나 필요한 상태가 발생하지 않았다면 해당 기능 검증으로 계산하지 않는다.

## 9. 다음 계층화 재시도 절차 — 미래에 승인받은 작업용

### A. 최신 정상 상태를 먼저 고정

1. 사용자가 이번에는 실제 계층화를 진행하라고 요청했는지 확인한다. 이 문서만 읽고 작업을 시작하지 않는다.
2. 최신 HEAD, 작업 트리·스테이징 변경, 에디터의 미저장 상태, 로컬호스트가 사용하는 프로젝트·포트를 확인한다. 다른 작업의 파일을 덮어쓰지 않는다.
3. 실제 작업이 허용된 다음 별도 `codex/` 브랜치와 격리된 작업 복사본 또는 worktree를 준비한다. 진행 중 게임이 읽는 public을 실험 산출물로 덮어쓰지 않는다.
4. 에디터 소스, public 패키지, geometry·재질·텍스처 목록, 프로젝트 설정, 런타임 보정 코드를 같은 시점의 기준선으로 기록한다. Git에 없는 필요한 파일도 누락 없이 보존한다.
5. 동일 맵·카메라·해상도·초기 상태에서 정상 게임 화면과 에디터 Graph를 기록한다. 최소한 정지, 좌우 이동, 구름·배경, 소켓/VFX 위치를 포함한다.

### B. 아무 계층도 바꾸지 않은 저장 왕복부터 시험

격리본을 에디터에서 열고 **모델 수정 없이 저장 → 닫기 → 다시 열기 → 후보 패키징**만 수행한다. 이때 이미 부모·노드·geometry·텍스처가 사라진다면 계층화 단계로 넘어가지 않는다.

특히 이번에는 정상 public에만 존재하던 구름이 있었다. 모선과 무관한 소스/public 불일치를 먼저 발견하되, 이를 고치는 실제 변경은 범위를 설명하고 별도 단계로 승인받는다. 계층화에 몰래 포함하지 않는다.

### C. 관리용 부모만 최소 단위로 추가

1. 에디터가 변환을 바꾸지 않는 순수 폴더 기능을 제공하는지 현재 버전에서 확인한다. 확인하지 않은 기능 이름이나 UI를 가정하지 않는다.
2. TransformNode가 필요하면 기존 VisualRoot 아래에 변환이 없는 ModelRoot부터 추가한다. GameplayRoot·VisualRoot 자체의 변환과 소켓 관계는 보존한다.
3. 먼저 작은 파츠 하나로 저장·재열기·런타임 외형을 검증한 다음 나머지로 확장한다.
4. 메시 59개를 Hull 7 / Ring 4 / Armor 32 / Reactor 4 / Emitter 12로 분류한다. 이름·geometry·material·UV·메시 수를 유지한다.
5. 에디터 메타데이터와 실제 parent 참조를 함께 확인한다. 과거 실행에서 얻은 숫자 uniqueId를 새 장면에 무조건 하드코딩하지 않는다.
6. 런타임 복구 helper와 함께 동작하는 상태를 먼저 검증한다. helper 제거·배율 재설계·모델 병합·새 GLB 변환을 같은 작업에 끼워 넣지 않는다.

### D. 후보 산출물을 검사한 후에만 로컬호스트로 전달

현재 packer가 독립 출력 경로를 지원하는지 확인하고, 지원하지 않으면 격리된 복사본에서 패키징한다. 존재하지 않는 옵션을 만들어 사용하지 않는다.

소스 diff의 허용 범위는 사전에 정한 모선 관리용 부모와 필요한 부모 메타데이터다. 비모선 데이터 변경은 기본적으로 예상 밖의 변경으로 취급한다. packer가 geometry 파일명을 바꿨다면 이름이 아니라 내용 해시와 모든 참조의 유효성을 대조한다.

후보 public 검사와 에디터 재열기 확인이 끝난 뒤에만 작업 중인 로컬호스트에 반영한다. 실제로 요청되는 `battlescene.babylon`이 후보와 같은지도 확인한다.

## 10. 즉시 중단하고 되돌려야 할 조건

- 모선 이외의 배경·카메라·지상 좌표가 변경됨.
- 그룹화 후 Y·스케일·기울기·원근 형태를 새 숫자로 다시 맞춰야 정상처럼 보임.
- 구름 등 필수 노드가 없어지거나 부모가 해석되지 않음.
- 패널 숫자만 바뀌고 실제 오브젝트가 움직이지 않음.
- 빌드는 통과하지만 전후 화면이 달라짐.
- 실행 중 에디터가 예전 메모리 상태를 다시 저장하거나, 다른 작업이 같은 파일을 변경함.

실패 시 현재 실패본과 diff를 보존한 뒤 **이번 시도 시작 시점의 기준선**으로 해당 시도의 소스·패키지·필요한 코드 변경을 함께 되돌린다. “모든 parent를 null로 만들기”를 원복으로 사용하지 않는다. 직전 HEAD가 이미 손상된 커밋인지도 확인한다.

프로젝트 전체 `reset --hard`, 광범위한 파일 복구, 다른 작업까지 포함된 커밋 통째 revert는 사용하지 않는다. 범위가 확실하지 않으면 사용자에게 해당 범위만 질문한다. public 일부만 되돌릴 경우 geometry·재질 참조가 그 버전과 짝이 맞는지 반드시 확인한다.
